# Risk Intelligence Graph Design

## Status

Approved for implementation planning.

## Context

The product already collects and renders market, news, macro, policy, search evidence, sector, portfolio, and performance artifacts. It also has a `/policy` page, dashboard surfaces, ticker detail pages, and output health checks. The new request is broader than the current policy impact feature: connect policy, security, and social issues as a network map so the user can understand how risk can spread into sectors, industries, watchlist names, and holdings.

The chosen long-term direction is a Full Intelligence Graph. To keep the first implementation safe and useful, the first build slice is Graph Core First. The first version creates a durable observational graph contract and alert scoring system before building a fully polished visual explorer.

## Goals

- Detect policy, security, and social issue risk before it fully reaches individual tickers.
- Model relationships as an explainable graph of issues, regions, policies, security themes, social clusters, sectors, tickers, and sources.
- Support sector and industry level early warnings even when no current holding is directly named yet.
- Use domain inference as a first-class relationship type, but keep it auditable with `domain_rules` references.
- Include social/community signals as early detection input without allowing rumor-like spikes to become hard alerts by themselves.
- Surface dashboard warnings in Korean by default.
- Preserve official `buy` / `watch` / `avoid` decisions as read-only context. The graph is observational in the first version.
- Keep cost bounded through daily batch generation, cache reuse, and limited manual node refresh.

## Non-Goals

- No always-on real-time monitoring in the first version.
- No trading automation or automatic decision changes.
- No graph database migration in the first version.
- No unbounded web search, social scraping, or provider calls.
- No social-only hard alerts.
- No external Tier 2 web search provider calls in the Phase 1 daily batch. Phase 1 reserves Tier 2 schema and cache contracts only; Tier 2 ingestion starts with Phase 3 manual refresh.
- No live Tier 3 social/community ingestion in Phase 1. Phase 1 defines schema support and guardrails; live social sources require a later licensing/API review phase.
- No replacement of the existing `/policy` page. Policy impact remains a policy/regulation report, while Risk Intelligence Graph is the broader policy/security/social risk layer.
- No polished full-screen graph explorer as the first deliverable. The first deliverable must make the graph data contract trustworthy.

## Product Shape

The feature has two user-facing layers:

1. Dashboard alert summary
2. Network detail surface

The dashboard is the primary entry point because the main use case is early warning. It shows top `주의` and `경보` items with affected sectors, exposed tickers, evidence counts, and Korean summaries. Lower-confidence `관찰` items can be visible in a secondary or collapsed area.

The network detail surface can initially be a simple structured view that consumes the full graph payload. A richer click-to-expand visual map can be added after the graph contract is stable.

User-facing copy must keep the existing `/policy` page and Risk Intelligence Graph distinct:

- `/policy`: reports policy/regulation events and their ticker impact scores.
- Risk Intelligence Graph: warns how policy, security, and social issues can propagate through regions, sectors, tickers, evidence, and market reaction paths.

## Architecture Boundary

The first version adds an observational graph core that consumes finalized pipeline outputs and bounded refresh results.

```text
existing artifacts + bounded refresh inputs
-> risk intelligence graph core
-> risk_intel_graph.json + risk_intel_summary.json + risk_intel_refresh_log.json
-> dashboard alert summary + later network detail page
```

The graph core owns:

- stable node and edge schema
- evidence type and confidence normalization
- alert level scoring
- Korean display fields for frontend rendering
- manual node refresh cache contract
- output health validation

The graph core does not own:

- official ticker decision changes
- model routing changes
- factor weight changes
- provider configuration changes outside its bounded source policy
- full visual explorer polish

## Source Tiers

### Tier 1: Existing Pipeline Artifacts

Tier 1 is preferred whenever possible because it is already generated by the daily pipeline.

Examples:

- `output/data/policy_impact.json`
- `output/data/search_evidence.json`
- market/news/macro/sector artifacts
- price and sector ETF reaction data
- portfolio and watchlist exposure
- existing output health/performance telemetry where relevant

Tier 1 is refreshed by the normal daily batch.

### Tier 2: Limited Web Search

Tier 2 adds bounded search evidence for policy, security, and issue context.

Allowed source families:

- official policy documents
- government or regulator pages
- reputable news sources
- company filings, IR, or SEC documents
- configured search providers such as OpenAI web search when explicitly enabled

Tier 2 results are cached by issue/node and normalized query hash. Default TTL should start at 24 hours.

Phase 1 must not call Tier 2 providers during the daily batch. It should define Tier 2 source types, cache key rules, provider status values, and health-check expectations only. Live Tier 2 ingestion begins with Phase 3 manual node refresh so provider failures, query normalization, cache TTL, and budget counters can be handled in the same bounded workflow.

### Tier 3: Social And Community Signals

Tier 3 provides early detection only.

Examples:

- Reddit
- X
- forums
- community trend clusters
- other configured social/community sources

Social signals can create `관찰` items and can contribute to `주의` only when corroborated. They cannot create `경보` on their own.

Phase 1 supports the `social` node/evidence type in schema, fixtures, scoring caps, and health checks only. Live Tier 3 ingestion should be a later phase after source licensing, API access, rate limits, and moderation/noise policy are reviewed. Until then, `source_tier_status.social.status` should be `skipped_not_enabled` unless fixture data is used in tests.

Default TTL should be shorter than Tier 2, such as 6 to 12 hours, because social signals age quickly.

## Manual Node Refresh

Manual refresh is node based.

Input:

- `node_id`
- optional refresh intent such as issue refresh, sector refresh, or selected node neighborhood refresh

Scope:

- 1-hop neighborhood by default
- 2-hop only when explicitly allowed by config or UI action
- bounded provider calls
- daily request cap
- cache reuse by `node_id`, source tier, and normalized query hash

Manual refresh quota resets at midnight in `Asia/Seoul` unless config explicitly overrides it. The refresh log should include `reset_timezone` and `reset_at_local`.

The normalized query hash should be derived from:

- canonical node id
- refresh intent
- source tier
- provider profile
- max hop scope
- normalized query text
- run date or cache date bucket

Query text normalization should use Unicode NFKC normalization, trim and collapse whitespace, lowercase Latin text, preserve ticker casing through a separate ticker list, strip punctuation that does not change meaning, and apply configured synonym/canonical mappings before hashing.

Output:

- a graph patch candidate
- refresh log row
- cache/provider counters

Manual refresh never mutates official decisions. It updates only the graph snapshot or a pending graph patch, depending on implementation phase.

Phase 3 manual refresh should not overwrite `risk_intel_graph.json` directly. It should write a pending patch candidate into the refresh log or a separate `risk_intel_graph_patch_{refresh_id}.json` artifact. The next daily batch can absorb accepted patch evidence into the canonical graph.

Patch lifecycle values:

- `pending`
- `applied`
- `rejected`
- `expired`

Refresh run example:

```json
{
  "refresh_id": "refresh:2026-05-19-001",
  "base_graph_run_id": "run:2026-05-19-batch",
  "node_id": "issue:us-china-ai-chip-export-control:2026q2",
  "patch_status": "pending",
  "patch_candidate": {
    "added_nodes": [],
    "added_edges": [],
    "added_source_records": [],
    "updated_nodes": []
  },
  "validation_result": {
    "passed": true,
    "issues": []
  },
  "requested_at": "2026-05-19T14:30:00+09:00",
  "expires_at": "2026-05-20T00:00:00+09:00"
}
```

When populated, `validation_result.issues[]` should use a typed structure so Phase 3 manual refresh errors can be rendered without schema changes:

```json
{
  "code": "missing_inference_refs",
  "severity": "error",
  "path": "patch_candidate.added_edges[0].inference_refs",
  "ref_id": "edge:issue:export-control:sector:semiconductors",
  "message_ko": "추론 엣지에 도메인 룰 참조가 없습니다."
}
```

Allowed `validation_result.issues[].severity` values are `info`, `warning`, and `error`.

## Generation Identity

All three artifacts must share a batch identity when they are produced together.

- `generation.run_id` is required in `risk_intel_graph.json`, `risk_intel_summary.json`, and `risk_intel_refresh_log.json`.
- `generation.as_of` should match root `as_of`.
- `risk_intel_summary.json` must include `derived_from_graph_run_id`.
- The batch order is graph first, then summary derived from that exact graph snapshot, then refresh log updated with the graph run id.
- A manual refresh run should get its own `refresh_id` and record the `base_graph_run_id` it used.

The dashboard should treat graph/detail data as mismatched if `risk_intel_summary.derived_from_graph_run_id` differs from `risk_intel_graph.generation.run_id`.

## Graph Schema

The JSON keys should use stable English snake_case. User-facing labels and summaries must be Korean.

### Schema Versioning

`schema_version` follows semantic versioning. The first release is `1.0.0`.

- Frontend consumers should render normally only when the major version matches.
- Major-version mismatch renders a Korean degraded state with the version values.
- Minor-version additions must be backward compatible.
- Breaking changes require a migration note in `generation.migration_note`.

### Node Types

Supported first-version node types:

- `issue`: a concrete issue or event, such as export control tightening or a port strike
- `policy`: a policy/regulation category, such as `export_control`, `tariff`, `defense_budget`
- `security`: a security theme, such as maritime security, cyber risk, military tension, supply chain security
- `social`: a social/community trend cluster
- `region`: country or region, such as US, China, Taiwan, EU, Middle East
- `sector`: investable sector or industry group
- `ticker`: watchlist or portfolio ticker
- `source`: optional display node for an article, policy document, filing, social cluster, or market reaction record

Each node should include:

```json
{
  "id": "issue:export-control-tightening",
  "canonical_id": "issue:export-control-tightening",
  "aliases": ["issue:semiconductor-export-restriction-expansion"],
  "node_type": "issue",
  "label": "Export control tightening",
  "label_ko": "수출통제 강화",
  "summary_ko": "반도체와 AI 칩 공급망에 부담이 될 수 있는 정책 리스크입니다.",
  "status": "active",
  "first_seen": "2026-05-19",
  "last_seen": "2026-05-19"
}
```

Node ids should be stable slugs, but semantic duplication is expected in issue data. Each node therefore reserves:

- `canonical_id`: the canonical node for scoring, search, and future merges
- `aliases`: alternate ids or normalized synonyms that should resolve to the same canonical node
- `merged_from`: optional historical ids absorbed into this node

Phase 1 does not need a full merge UI. It should reserve these fields and make builders resolve aliases before creating new issue nodes. Historical ids should not be silently rewritten; when a merge happens, old references should remain traceable through `canonical_id` and `merged_from`.

Issue node id format:

```text
issue:{canonical_topic_slug}[:{region_scope}][:{date_bucket}]
```

- `canonical_topic_slug`: kebab-case policy category or core issue keyword
- `region_scope`: optional region qualifier for geographically scoped issues
- `date_bucket`: optional quarter bucket such as `2026q2`; long-running issues can omit it

Examples:

- `policy:export_control`
- `issue:us-china-ai-chip-export-control:2026q2`
- `issue:taiwan-strait-tension:2026q2`
- `issue:red-sea-shipping-disruption`

Alias resolution order:

1. Builder loads an index of existing node `id`, `canonical_id`, and `aliases`.
2. If a new candidate id matches an existing id or alias, it resolves to the existing `canonical_id`.
3. If there is no exact match but normalized text is similar, it records a `pending_duplicate_candidates` entry.
4. Automatic merge is forbidden.
5. A reviewed merge can later absorb old ids through `merged_from`.

Alias normalization uses Unicode NFKC normalization, lowercase Latin text, whitespace normalization, punctuation removal, and configured synonym mapping.

`pending_duplicate_candidates` should be present at the graph root:

```json
{
  "pending_duplicate_candidates": [
    {
      "new_candidate_id": "issue:china-ai-chip-export-restriction:2026q2",
      "matched_canonical_id": "issue:us-china-ai-chip-export-control:2026q2",
      "similarity_score": 0.84,
      "detected_at": "2026-05-19",
      "status": "pending",
      "resolved_at": null,
      "resolved_by": null,
      "resolution_note": null
    }
  ]
}
```

Lifecycle values are `pending`, `merged`, `rejected`, and `expired`. `resolved_at`, `resolved_by`, and `resolution_note` are required when `status` is not `pending`. Phase 1 can leave all candidates pending, but the schema reserves the resolution fields so later operator review does not require a breaking change.

`source_records` are the canonical evidence table. `source` nodes are optional visual wrappers that can point to a `source_record_id` when the detail surface wants evidence records to appear inside the graph itself. `evidence_refs` must reference `source_records`, not arbitrary display nodes.

Example source record:

```json
{
  "id": "record:policy-doc-1",
  "source_type": "policy_document",
  "title": "Export control update",
  "title_ko": "수출통제 업데이트",
  "url": "https://example.gov/policy/export-control",
  "published_at": "2026-05-19",
  "trust_tier": "official",
  "summary_ko": "공식 정책 문서가 반도체 관련 수출통제 강화를 설명합니다."
}
```

Market reaction source records should use `source_type=market_reaction` and `trust_tier=market_data` so market confirmation scoring is deterministic.

Example market reaction record:

```json
{
  "id": "record:market-reaction-semiconductors-2026-05-19",
  "source_type": "market_reaction",
  "trust_tier": "market_data",
  "published_at": "2026-05-19",
  "target_id": "sector:semiconductors",
  "reaction_type": "sector_etf_drawdown",
  "reaction_strength": "moderate",
  "reaction_score": 0.50,
  "metric": "SMH 1d relative move vs SPY",
  "value": -0.028,
  "summary_ko": "반도체 ETF가 시장 대비 약세를 보여 중간 수준의 시장 확인 신호로 기록되었습니다."
}
```

`reaction_score` must be between 0 and 1. Default mapping is `strong=0.75`, `moderate=0.50`, `weak=0.25`, and `none=0.00`.

### Edge Types

Edges are first-class records. Every important relationship must be explainable.

Supported evidence types:

- `explicit`: directly supported by a source
- `inferred`: domain-map or supply-chain inference
- `social`: social/community signal
- `market`: price, ETF, volatility, or correlation confirmation

Supported relationship values should start small:

- `mentions`
- `affects`
- `inferred_affects`
- `reacts_to`
- `exposes`
- `corroborates`

Each edge should include:

```json
{
  "id": "edge:issue:export-control-tightening:sector:semiconductors",
  "source_id": "issue:export-control-tightening",
  "target_id": "sector:semiconductors",
  "relationship": "inferred_affects",
  "relationship_label_ko": "영향 가능",
  "evidence_type": "inferred",
  "evidence_label_ko": "도메인 추론",
  "confidence": 0.72,
  "severity_delta": -0.6,
  "evidence_refs": ["record:policy-doc-1"],
  "inference_refs": ["rule:export-control-semiconductors-v1"],
  "explanation_ko": "수출통제 강화는 반도체 장비와 AI 칩 공급망에 부담으로 연결될 수 있습니다.",
  "created_at": "2026-05-19T00:00:00+09:00",
  "updated_at": "2026-05-19T00:00:00+09:00"
}
```

Inference edges must cite a domain rule through `inference_refs`. An inferred edge without valid `inference_refs` should fail health validation.

`evidence_refs` and `inference_refs` are intentionally separate:

- `evidence_refs` reference `source_records`. They support the existence or relevance of the issue itself, such as a policy document, news article, filing, or market reaction record.
- `inference_refs` reference `domain_rules`. They support why an issue can propagate to the target node through a domain or supply-chain relationship.
- `explicit` edges do not require `inference_refs`.
- `inferred` edges require both non-empty `evidence_refs` and non-empty `inference_refs`.
- Every edge must include a non-empty Korean `explanation_ko`.

### Domain Rules

`risk_intel_graph.json` includes a root `domain_rules[]` array. These rules are the auditable source for inferred edges.

Example:

```json
{
  "domain_rules": [
    {
      "id": "rule:export-control-semiconductors-v1",
      "version": "2026-05-01",
      "source_type": "internal_domain_map",
      "title": "Export controls affect semiconductor equipment and AI chip supply chains",
      "title_ko": "수출통제는 반도체 장비/AI 칩 공급망에 영향",
      "rationale_ko": "수출통제는 반도체 장비, AI 칩, 파운드리 공급망에 영향을 줄 수 있습니다.",
      "rule_confidence": 0.75,
      "last_reviewed": "2026-05-01"
    }
  ]
}
```

Health checks must validate that every `inference_refs[]` id exists in `domain_rules[].id` and `rule_confidence` is between 0 and 1.

A domain rule is stale when `last_reviewed` is more than one year before `generation.as_of`. The artifact is marked `degraded` when at least one alert path with `alert_level != observation` references a stale domain rule. Stale rules that are unused, or used only by `observation` paths, should remain renderable and be listed in `health_warnings[]` instead of changing artifact status.

`confidence` and `severity_delta` are separate:

- `confidence` is the reliability of the relationship and its evidence, from 0 to 1.
- `severity_delta` is the expected directional impact on the target node, from -1 to 1.
- Negative values mean adverse risk/headwind. Positive values mean favorable tailwind or risk relief.
- Magnitude is impact strength, not certainty. Example: `-0.6` means a moderately strong adverse effect if the relationship is valid; the reliability of that relationship is still represented by `confidence`.
- Risk alert scoring uses downside severity as `max(0, -severity_delta) * confidence`. Positive values can be shown as context or offsetting tailwind, but they do not trigger risk warnings by themselves.

Default edge confidence ranges should be versioned under `confidence_config_version` or the broader `scoring_config_version`:

Explicit edges:

- source directly states the relationship: `0.80` to `0.95`
- source mentions both entities but relation is weak: `0.45` to `0.65`

Inferred edges:

- high-confidence domain rule with clear target mapping: `0.65` to `0.80`
- medium-confidence domain rule: `0.45` to `0.65`
- stale rule or broad mapping: `0.25` to `0.45`

Market edges:

- strong reaction with clean target mapping: `0.70` to `0.85`
- moderate reaction: `0.45` to `0.65`
- weak or noisy reaction: `0.20` to `0.40`

Social edges:

- corroborated social cluster: `0.35` to `0.55`
- uncorroborated social cluster: `0.20` to `0.35`

`confidence_config_version` tracks changes to the default edge confidence range tables. Changes must run regression tests against fixtures that assert each evidence type produces confidence within the expected band.

## Alert Scoring

Alert levels:

- `observation`: `관찰`
- `warning`: `주의`
- `alert`: `경보`

Score inputs:

- evidence strength
- graph proximity from issue to sector/ticker
- portfolio, watchlist, or core-sector exposure
- social momentum
- market confirmation
- freshness

### Initial Phase 1 Numeric Model

Phase 1 should ship with explicit default weights instead of leaving scoring to implementer judgment.

Risk score range: 0 to 1. `raw_score` is the weighted score before caps. `score` is the final score after caps and guardrails.

```text
raw_score =
  0.30 * evidence_strength
+ 0.20 * proximity_score
+ 0.20 * exposure_score
+ 0.15 * market_confirmation_score
+ 0.10 * downside_severity_score
+ 0.03 * social_momentum_score
+ 0.02 * freshness_score
```

Default thresholds:

- `alert`: final `score >= 0.70` and all hard guardrails pass
- `warning`: `0.40 <= score < 0.70`, or a warning guardrail explicitly promotes a corroborated item
- `observation`: `score < 0.40`, or any cap/guardrail prevents promotion

Caps:

- social-only paths are capped at `0.39`
- inference-only paths are capped at `0.49`
- single low-quality source paths are capped at `0.39`
- paths without valid `evidence_refs` cannot exceed `warning` and cannot appear as dashboard `alert`

Final score semantics:

- `raw_score` is the weighted sum of `score_breakdown`.
- `cap_value` is `null` when no cap applies, otherwise the lowest applicable cap.
- `score = min(raw_score, cap_value)` when a cap applies.
- `score = raw_score` when no cap applies.
- `score_kind` is `final` when no cap applies and `capped_final` when a cap applies.

Evidence strength:

- Use the `trust_tier` score map from the Enums section as the single source of truth.
- Builders and tests should import or mirror that map from one local constant, not duplicate the numeric values in separate scoring code.

When multiple evidence records support one path, use the maximum source strength plus `0.05` for each additional independent non-social evidence type, capped at `1.00`.

Path discovery and proximity:

- Use BFS only to discover candidate paths within the allowed hop scope.
- Score discovered paths with confidence and hop decay, not raw BFS depth alone.
- `path_confidence` is the geometric mean of edge confidence values on the path.
- `hop_decay` defaults to `1.00` for 1 hop, `0.75` for 2 hops, and `0.55` for 3 hops.
- `proximity_score = path_confidence * hop_decay`.
- Daily batch alert scoring should use up to 3 hops; manual node refresh uses 1 hop by default and 2 hops when explicitly requested.

Exposure score:

- directly held ticker: `1.00`
- watchlist ticker: `0.75`
- configured core sector: `0.60`
- affected sector without direct watchlist/holding exposure: `0.35`
- no relevant exposure: `0.00`

Configured core sectors come from `config/sectors.yaml`, or from the generated `output/data/sectors.json` mirror when the graph builder is running from output artifacts only. A sector qualifies for the `0.60` core-sector exposure score when its canonical sector id matches a configured sector id or a configured sector ticker universe. If no core sector config is present, no sector receives the core-sector score and affected sectors fall back to `0.35`.

Market confirmation score:

- strong ETF/price/volatility/correlation reaction: `0.75`
- moderate reaction: `0.50`
- weak reaction: `0.25`
- no market confirmation: `0.00`

Social momentum score:

```text
social_momentum_score =
  0.50 * volume_spike_norm
+ 0.30 * persistence_norm
+ 0.20 * source_diversity_norm
```

Each normalized input is clamped to 0 to 1. Without non-social corroboration, social momentum can raise visibility but remains subject to the social-only cap.

Freshness score:

- Tier 1 and Tier 2 half-life: 72 hours
- Tier 3 social half-life: 12 hours
- `freshness_score = 0.5 ** (age_hours / half_life_hours)`

Downside severity score:

- For each edge, `edge_downside = max(0, -severity_delta) * confidence`.
- For a path, `downside_severity_score` is the maximum edge downside on the path.
- Positive `severity_delta` values are displayed as tailwind/risk relief context, but do not increase downside risk score.

These defaults should be versioned as `scoring_config_version` in the graph `generation` block so future tuning can be traced.

Path-level aggregation rules:

- `path_score` is calculated per candidate path.
- For the same `(canonical_issue_id, target_group)`, use the maximum candidate `path_score` as the representative score.
- `target_group` is either sector-level or ticker-level.
- `evidence_strength` is calculated from the union of `evidence_refs` on the path.
- Start from the strongest `source_records[].trust_tier` score.
- Add `0.05` for each additional independent non-social evidence type, capped at `1.00`.
- `exposure_score` uses the strongest exposure among the path targets.
- `market_confirmation_score` uses the maximum of either an `evidence_type=market` edge confidence or the reaction strength of a market `source_record` connected to the target sector/ticker.
- `proximity_score = path_confidence * hop_decay`.
- Candidate paths containing any edge with `confidence < 0.20` are excluded from discovery output.

Double-counting prevention:

- `evidence_strength` is based on `source_records[].trust_tier`.
- `edge.confidence` is the reliability of the relationship between two nodes, based on whether a source states the relationship directly, a domain rule supports it, or market/social evidence corroborates it.
- These inputs are independent. Builders must not set `edge.confidence = source.trust_score` as a shortcut.
- Tests must cover same-source/different-relationship and same-relationship/different-source cases.

Positive severity handling:

- Positive `severity_delta` is displayed as a mitigating or tailwind context.
- It does not increase `raw_score` or final `score`.
- When positive and negative paths exist for the same issue, dashboard card title and score are based on the negative path, and positive paths appear in a `완화 요인` section.

### Promotion Rules

`관찰`:

- social spike only
- inference-only path with `score < 0.40`
- inference-only path without direct exposure
- inference-only path with stale or low-confidence domain rules
- single weak source only
- no direct portfolio/watchlist/core-sector exposure

`주의`:

- explicit source exists
- inference-only path may become `warning` when `score >= 0.40`, valid `domain_rules` exist, `exposure_score >= 0.60` or the affected sector is a configured core sector, and no hard guardrail blocks promotion
- social spike plus web/news corroboration
- relevant sector ETF, price, volatility, or correlation reaction exists
- issue is within 1 to 2 hops of a core sector

`경보`:

- direct portfolio/watchlist exposure or core-sector exposure exists
- at least two non-social evidence types overlap
- or explicit evidence plus market confirmation exists
- all alert paths include evidence references

Hard guardrails:

- Social-only cannot become `경보`.
- A low-quality single source remains `관찰`.
- Inference edges must cite a domain-map rule.
- Manual refresh cannot mutate official decisions.
- Any dashboard `경보` card must include evidence references.

## Error Handling

Missing Tier 1 artifact:

- produce partial graph when possible
- set graph status to a partial or degraded state
- record missing input
- show Korean empty/degraded state in the UI

Tier 2 or Tier 3 provider failure:

- use cached data when available
- skip failed tier when cache is unavailable
- record provider failure in refresh log
- do not fail the daily pipeline solely because a supplemental provider failed

Korean summary failure:

- preserve original title
- provide enum label fallback in Korean
- set `summary_ko` to a safe fallback
- keep UI renderable

Weak evidence:

- treat as `관찰`, not as an error
- do not promote to dashboard `경보`

Schema violation:

- output health issue
- invalid JSON, broken references, out-of-range confidence/severity, or missing required Korean display fields should fail validation

## Status Semantics

Artifact status values must be consistent across graph, summary, and refresh log.

`ok`:

- every `required_inputs.tier1_required` input has `input_status.status=present`
- JSON is valid
- graph references are valid
- dashboard cards have required Korean display fields

`partial`:

- JSON and references are valid
- every `required_inputs.tier1_required` input is present
- optional Tier 1 inputs or Tier 2/3 inputs may be `missing`, `skipped_not_enabled`, `cache_only`, or `stale`

`degraded`:

- JSON and references are valid
- at least one required Tier 1 input is `missing`, but fewer than 50% of required Tier 1 inputs are missing
- or provider/cache failures materially reduce evidence coverage
- or summary is derived from an older graph snapshot because the newest graph failed validation
- or at least one `alert_paths[]` row with `alert_level != observation` references a stale domain rule

`error`:

- JSON is invalid
- required root shape is invalid
- graph has no usable nodes because configured required inputs failed
- 50% or more `required_inputs.tier1_required` inputs are missing
- `risk_intel_summary.derived_from_graph_run_id` does not match `risk_intel_graph.generation.run_id`
- required Korean display fields for visible dashboard cards are missing

`partial` and `degraded` should render Korean status badges in the UI. `error` should render a Korean empty/error state and suppress hard alert cards.
